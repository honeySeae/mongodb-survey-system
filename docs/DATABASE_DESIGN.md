# 问卷系统数据库设计（第一阶段）

> 数据库：MongoDB。所有数据存储在 MongoDB 中，不使用关系数据库。

## 一、集合总览

| 集合 | 作用 | 一条文档代表 |
|---|---|---|
| `users` | 用户账号（创建者和填写者是同一种用户） | 一个用户 |
| `surveys` | 问卷，**题目嵌入其中** | 一份问卷 |
| `responses` | 填写结果 | 一次提交 |

同一个用户既可以创建问卷，也可以填写别人的问卷。他与某份问卷的关系由 `surveys.ownerId`（创建者）和 `responses.respondentId`（填写者）表示，不区分用户类型。

## 二、users

| 字段 | 类型 | 必填 | 说明 |
|---|---|---|---|
| `_id` | ObjectId | 是 | 自动生成 |
| `username` | String | 是 | 唯一 |
| `passwordHash` | String | 是 | bcrypt 加密，不存明文 |

```js
  username: "zhangsan",

  createdAt: ISODate("2026-10-19T10:00:00Z")
}
```

## 三、surveys

| 字段 | 类型 | 必填 | 说明 |
|---|---|---|---|
| `_id` | ObjectId | 是 | |
| `ownerId` | ObjectId | 是 | 创建者，关联 `users._id` |
| `shortCode` | String | 是 | 访问链接 `/survey/<shortCode>`，唯一，系统随机生成：6 位大小写字母和数字，区分大小写（如 `a8Kx2p`）；重复时重新生成。完整链接 = `.env` 的 `PUBLIC_BASE_URL` + `/survey/<shortCode>`，**链接本身不存库**，更换部署地址无需改数据。例外：示例数据脚本 `scripts/seed_demo.py` 为示例问卷指定固定值 `Food26`（服务层的可选参数，网页和接口不接受；已被占用时报错，不覆盖） |
| `title` | String | 是 | 问卷标题，去首尾空格后 1~100 个字符 |
| `description` | String | 否 | 问卷说明，0~1000 个字符；未填写时存空字符串 |
| `status` | String | 是 | `draft` 草稿 / `published` 已发布 / `closed` 已关闭 |
| `settings.allowAnonymous` | Boolean | 是 | 是否匿名（见“匿名方案”） |
| `settings.submissionPolicy` | String | 是 | `once` / `latest` / `all`（见“提交策略”） |
| `settings.deadline` | Date | 否 | 截止时间，`null` 表示不限。统一存 UTC；接口要求带时区，设置时必须晚于当前时间 |
| `version` | Number | 是 | 问卷版本号，初始为 1；为第二阶段“修改已发布问卷”预留 |
| `questions` | Array | 是 | 题目数组，**数组顺序即默认答题顺序** |
| `createdAt` / `updatedAt` | Date | 是 | |
| `publishedAt` / `closedAt` | Date | 否 | |

### 3.1 题目结构（`questions` 数组的每一项）

| 字段 | 类型 | 必填 | 说明 |
|---|---|---|---|
| `id` | String | 是 | 稳定 id，**由系统生成**，问卷内唯一；跳转规则和答卷都引用它，不用“第几题”。格式 `q_` + 6 位随机字符（小写字母和数字，如 `q_k3x9ab`） |
| `type` | String | 是 | `single_choice` / `multiple_choice` / `text` / `number` |
| `title` | String | 是 | 题目文字，去首尾空格后 1~200 个字符 |
| `options` | Array | 选择题必填 | `[{ id, text }]`，选项 id 由系统生成，问卷内唯一，格式 `o_` + 6 位随机字符；1~50 个选项，每项文字 1~100 个字符，同一题内文字不重复；文本题、数字题不能有 `options` |
| `validation` | Object | 是 | 校验规则，见 3.2 |
| `logic` | Object | 否 | 跳转规则，见 3.3；文本题没有 |

选项使用对象 `{id, text}` 而不是纯字符串，以便将来扩展（如选项配图 `media`）。

id 采用随机字符而不是递增序号：不需要在问卷中额外存计数器字段，删除题目后 id 也不会被复用；生成时检查问卷内不重复。下文示例中的 `q1`、`o1` 只是为了阅读方便的简写。

### 3.2 validation（校验规则）

| 题型 | 字段 | 说明 |
|---|---|---|
| 所有题 | `required` | 是否必答；布尔值，未填写时保存为 `false` |
| 多选 | `minSelect`, `maxSelect` | 最少/最多选几个；“必须选 2 个”表示为 `minSelect: 2, maxSelect: 2` |
| 文本 | `minLength`, `maxLength` | 最少/最多字数 |
| 数字 | `min`, `max`, `integerOnly` | 最小值、最大值、是否必须为整数 |

未设置的字段表示不限制（`integerOnly` 未设置等同于 `false`）。

**保存题目时对设置本身的检查**（不合法则拒绝保存）：
- `minSelect`、`maxSelect` 为正整数，`minSelect ≤ maxSelect ≤ 选项数`；
- `minLength` 为非负整数，`maxLength` 为 1~10000 的整数，`minLength ≤ maxLength`；
- `min`、`max` 为数字，`min ≤ max`；`required`、`integerOnly` 为布尔值；
- 类型严格：布尔值不当作数字，字符串 `"3"` 不当作数字 3；
- **字段与题型不匹配直接拒绝**（如数字题写了 `minLength`、文本题写了 `options`），不静默忽略。第二阶段新增字段时同步修改检查规则。
- 每份问卷最多 100 道题。

### 3.3 logic（跳转规则）

```js
logic: {
  rules: [
    { when: { op: "<运算符>", value: <值> }, goto: "<目标题 id 或 END>" }
  ],
  defaultNext: null      // 没有规则命中时去哪；null = 顺序进入下一题
}
```

| 题型 | 运算符 | value 格式 |
|---|---|---|
| 单选 | `eq` | 选项 id |
| 单选 | `in` | 选项 id 数组 |
| 多选 | `contains` | 选项 id |
| 多选 | `containsAny` / `containsAll` / `equals` | 选项 id 数组 |
| 数字 | `eq` `ne` `gt` `gte` `lt` `lte` | 数字 |
| 数字 | `between` | `[最小, 最大]`，包含两端 |
| 文本 | 不支持跳转 | |

`goto: "END"` 表示直接结束问卷。

补充约定：
- 规则中引用的选项 id 必须是**本题**的选项；数组形式的值不能为空、不能有重复；`between` 恰好两个数且最小值 ≤ 最大值；数字值不能是布尔值。
- `defaultNext` 只能是 `null`、`END` 或当前题之后某道题的 id。
- 每道题最多 50 条规则；规则和 `when` 中不能有多余字段。
- 运算符表在代码中只定义一处（`app/logic/operators.py`），保存时的检查和填写时的路径计算共用。

### 3.4 示例

```js
{
  _id: ObjectId("..."),
  ownerId: ObjectId("..."),
  shortCode: "a8Kx2p",
  title: "水果偏好调查",
  description: "了解大家吃水果的习惯",
  status: "published",
  settings: {
    allowAnonymous: true,
    submissionPolicy: "latest",
    deadline: ISODate("2026-11-30T23:59:59Z")
  },
  version: 1,
  questions: [
    {
      id: "q1", type: "single_choice", title: "你喜欢吃水果吗？",
      options: [ { id: "o1", text: "喜欢" }, { id: "o2", text: "不喜欢" } ],
      validation: { required: true },
      logic: { rules: [ { when: { op: "eq", value: "o2" }, goto: "q5" } ], defaultNext: null }
    },
    {
      id: "q2", type: "multiple_choice", title: "你喜欢哪些水果？",
      options: [
        { id: "o3", text: "苹果" }, { id: "o4", text: "香蕉" },
        { id: "o5", text: "西瓜" }, { id: "o6", text: "榴莲" }
      ],
      validation: { required: true, minSelect: 1, maxSelect: 3 },
      logic: {
        rules: [ { when: { op: "contains", value: "o6" }, goto: "q3" } ],
        defaultNext: "q4"
      }
    },
    {
      id: "q3", type: "text", title: "为什么喜欢榴莲？",
      validation: { required: false, minLength: 5, maxLength: 200 }
    },
    {
      id: "q4", type: "number", title: "你每周吃几次水果？",
      validation: { required: true, min: 0, max: 50, integerOnly: true },
      logic: { rules: [ { when: { op: "eq", value: 0 }, goto: "END" } ], defaultNext: null }
    },
    {
      id: "q5", type: "text", title: "其他建议",
      validation: { required: false, maxLength: 500 }
    }
  ],
  createdAt: ISODate("..."), updatedAt: ISODate("..."), publishedAt: ISODate("...")
}
```

## 四、responses

| 字段 | 类型 | 必填 | 说明 |
|---|---|---|---|
| `_id` | ObjectId | 是 | |
| `surveyId` | ObjectId | 是 | 关联问卷 |
| `surveyVersion` | Number | 是 | 填写时问卷的版本 |
| `respondentId` | ObjectId | 是 | 填写人，**始终记录**（匿名问卷不对创建者展示） |
| `isLatest` | Boolean | 是 | 是否为该填写人在该问卷上最新的一份；所有提交策略下都维护 |
| `submittedAt` | Date | 是 | 提交时间 |
| `answers` | Array | 是 | `[{ questionId, value }]`，只存路径上实际作答的题 |

**value 格式：**

| 题型 | value | 例子 |
|---|---|---|
| 单选 | 选项 id（字符串） | `"o1"` |
| 多选 | 选项 id 数组 | `["o3", "o6"]` |
| 文本 | 字符串 | `"闻着臭吃着香"` |
| 数字 | 数值类型（不能存成字符串） | `7` |

```js
{
  _id: ObjectId("..."),
  surveyId: ObjectId("..."),
  surveyVersion: 1,
  respondentId: ObjectId("..."),
  isLatest: true,
  submittedAt: ISODate("2026-10-20T08:30:00Z"),
  answers: [
    { questionId: "q1", value: "o1" },
    { questionId: "q2", value: ["o3", "o6"] },
    { questionId: "q3", value: "闻着臭吃着香" },
    { questionId: "q4", value: 7 },
    { questionId: "q5", value: "无" }
  ]
}
```

## 五、索引

| 集合 | 索引 | 用途 |
|---|---|---|
| users | `{username: 1}` 唯一 | 登录查找、防止重名 |
| surveys | `{shortCode: 1}` 唯一 | 通过链接找到问卷 |
| surveys | `{ownerId: 1, createdAt: -1}` | “我的问卷”列表 |
| responses | `{surveyId: 1, submittedAt: -1}` | 统计、查看答卷 |
| responses | `{surveyId: 1, respondentId: 1}` 唯一，部分索引 `isLatest: true` | 保证每人每份问卷最多一份“最新”答卷；同时用于判断是否已填写 |
| responses | `{"answers.questionId": 1}` | 按题统计 |

说明：
- 原设计另有一个普通索引 `{surveyId: 1, respondentId: 1}` 用于“判断是否已填写”，与部分唯一索引键相同，**已删除**。凡是填写过的用户必然恰好有一份 `isLatest: true` 的答卷，所以“是否填写过”用 `{surveyId, respondentId, isLatest: true}` 查询即可命中部分唯一索引，结果等价。
- 部分唯一索引同时承担并发保护：同一用户并发提交时，最多一份答卷能成为“最新”；`once` 策略下重复提交也由它拦截（见 6.2）。

### 5.1 `$jsonSchema` 校验
- 由初始化脚本为三个集合创建 `$jsonSchema` 校验，只约束核心字段（必填字段、类型、枚举取值）。
- **不设置** `additionalProperties: false`，并使用 `validationLevel: "moderate"`（只校验新插入的文档和本来就符合规则的文档的更新）。这样第二阶段新增字段不会与数据库校验冲突，旧文档也不会因规则变化而无法更新。
- 更细的业务校验（跳转合法性、题型专属规则）在应用层完成。

## 六、业务规则约定

### 6.1 匿名方案：记录但不展示
- 填写问卷前必须登录（需求原文：“填写问卷的人需要先登录”）。
- `respondentId` 始终记录，用于判断重复填写。
- `allowAnonymous: true` 时，查看答卷和统计的接口**不返回**填写人信息。
- `allowAnonymous: false` 时：答卷列表返回填写人用户名；填空题（文本、数字）统计列出的每条内容附带填写人用户名。
- 实现方式（第八步）：用户名在聚合管道中用 `$lookup` 取得（只取 `username`）；**匿名问卷的管道不包含 `$lookup`，也不输出 `respondentId`**，在数据库查询层面保证不展示填写人（见 6.8）。无论是否匿名，都不返回 `respondentId` 本身。
- 作答人数（只是数字）匿名问卷也返回（见 6.7）。
- 取舍：数据库层面仍能知道是谁填的，换来的是能够支持“禁止重复填写”。
- 填写者看到的问卷（`GET /api/s/{shortCode}`）只包含 `allowAnonymous` 等设置，前端据此提示“本问卷为匿名问卷，创建者看不到你的身份”；不包含 `ownerId` 等内部字段。
- 填写者看到的题目只包含 `id`、`type`、`title`、`options`、`validation`（白名单），**不包含跳转规则 `logic`**：填写者只需要知道下一题（由路径预览接口给出），不需要知道为什么跳到那里，也就无法根据规则刻意选择答案（2026-10-19 开发者确认）。

### 6.2 提交策略 `submissionPolicy`

| 值 | 含义 | 适用场景 | 统计口径 |
|---|---|---|---|
| `once` | 每人只能填一次，再次提交被拒绝 | 普通调查 | 每人那一份 |
| `latest` | 可以重填，以最后一次为准 | 报名表、可修改答案 | 只算 `isLatest: true` |
| `all` | 可多次填写，每次都算 | 每日打卡、反馈收集 | 全部答卷 |

- 所有提交都保留，不覆盖、不删除（需求：“每次填写都应该被保存”）。
- 新提交时：把该用户在该问卷上旧的 `isLatest` 置为 `false`，新答卷置为 `true`。

**写入顺序**（单机 MongoDB 不支持事务，按以下顺序保证任何一步失败都不会让用户“没有最新答卷”）：

| 策略 | 写入步骤 |
|---|---|
| `once` | 直接插入 `isLatest: true` 的答卷。若该用户已有答卷，部分唯一索引报重复键错误 → 拒绝提交（返回 409）。并发重复提交也由索引拦截。 |
| `latest` / `all` | ① 插入新答卷，`isLatest: false`；② 把该用户在该问卷上其他 `isLatest: true` 的答卷置为 `false`；③ 把新答卷置为 `true`。第 ③ 步若因并发提交触发唯一索引冲突：**先删除第 ① 步刚插入的这份答卷，再返回 409**，提示稍后重试。这样“返回 409”一定表示“没有保存”。（2026-10-19 修正，见下方说明） |

- 第 ①~③ 步之间存在极短的窗口，此时该用户没有“最新”答卷，统计可能暂时少算一份；这是不使用事务的取舍。若将来改用副本集，可把这三步放进事务。
- `once` 策略下提交前也会先查询 `{surveyId, respondentId, isLatest: true}`，已填写时直接给出友好提示；索引是最终保证。

**第 ③ 步冲突处理的修正（2026-10-19，第七步实现时发现）**
- 原设计：第 ③ 步触发唯一索引冲突时“返回 409，提示稍后重试”。
- 问题：此时第 ① 步插入的答卷（`isLatest: false`）已经存入数据库。`all` 策略的统计口径是全部答卷，这份答卷会被统计；但用户收到的是“失败”，很可能再提交一次，于是同一次填写被算两次。`latest` 策略下也会留下一份用户以为没有保存的历史答卷。
- 修正：冲突时先删除自己刚插入的那份答卷，再返回 409，使“返回 409”与“没有保存”一致。这种冲突几乎只出现在同一个人连续点击提交的情况，撤销其中一份正好防止重复提交。
- 与“所有提交都保留、不删除”不矛盾：被撤销的是一次失败的提交，从未成功返回给用户。
- 未采用的方案：冲突时不报错，按提交时间决定哪份为最新。这样连续点击两次时两份都会保存，`all` 策略下仍会被算两次。

**提交与预填**
- 每次提交记录 `surveyVersion` 为提交时问卷的 `version`。
- 保存的 `answers` 是后端重算路径并规范化之后的结果（见 6.3、6.6），不是前端原样提交的内容。
- `latest` 策略下，填写者获取问卷时返回本人最新一份答卷的答案（`mySubmission.latestAnswers`），用于再次填写时预填（如报名表修改信息不必从头再填）；`once`、`all` 策略不返回。只返回本人自己的答案。
- 一次提交中的答案最多 200 项（题目最多 100 道，留有余量，同时防止超大请求）。

### 6.3 跳转规则约定
1. **第一条命中为准**：规则按数组顺序检查，第一条成立的生效。越具体的条件应放越前面（例如 `containsAll [A,B]` 放在 `contains A` 之前）。
2. **只能往后跳**：`goto` 必须是当前题之后的题或 `END`。**每次保存问卷时整体检查**（调整题目顺序也可能让规则变成往前跳），不合法则拒绝保存。
3. **结束**：`goto: "END"`；题目 id 由系统生成，不会与 `END` 冲突。
4. **选填题未作答**：不匹配任何规则，走 `defaultNext`（为 `null` 时顺序下一题）。
5. **被跳过的题**：不显示、不校验（即使必答）、不存储。
6. **后端重算路径**：提交时后端不信任前端，从第一题开始按答案和规则重新计算应经过的路径：
   - 路径上的必答题未答 → 拒绝提交，返回错误；
   - 路径外的多余答案 → 直接丢弃；
   - 路径上的每个答案 → 按其 `validation` 校验。
7. **校验与跳转分离**：`validation` 决定“能怎么答”，`logic` 决定“答完去哪”，互不影响。
8. **路径预览**：填写过程中，前端把已作答内容发给后端，由后端计算下一题并返回校验错误；跳转逻辑只在后端实现一份。**提交时后端仍然完整重算路径**，不依赖预览结果。
   - 预览与提交使用同一个路径计算函数，只在“答案中没有这道题”时不同：预览视为**还没答到**，停在这里并把它作为下一题返回；提交视为**未作答**。答案中有这道题但值为空（`null`、空白文本、`[]`）时，两种模式都视为未作答（选填题按第 4 条继续，必答题报错）。
   - **遇到第一个错误就停下，只返回这一个错误**（含必答题未答）：答案不合法时无法确定下一题，继续计算可能对实际不在路径上的题报错。
   - 同一道题在一次提交中出现两次 → 拒绝整个请求（无法判断以哪个为准）。
   - 答案中出现问卷里不存在的题目 id → 与路径外的答案一样丢弃，不报错。
   - 计算路径时若遇到往前跳（数据被绕过接口修改），按内部错误处理，避免死循环。
   - 运算符的判断方式：单选 `eq` 等于、`in` 属于列表；多选 `contains` 包含该项、`containsAny` 至少包含一项、`containsAll` 全部包含、`equals` 与列表完全相同（不看顺序）；数字按数值比较（`3` 与 `3.0` 相等），`between` 包含两端。
9. **编辑题目时的整体检查**：题目通过单题接口添加、修改、删除、调整顺序，每次修改后对整份问卷做一次检查，不合法则拒绝本次修改：
   - 跳转目标必须存在且在当前题之后（或为 `END`）；
   - 运算符必须与题型匹配，规则引用的选项 id 必须存在；`between` 的值满足 `最小 ≤ 最大`；
   - 删除被跳转规则引用的题目或选项 → 拒绝，并提示是哪条规则引用了它；
   - 调整顺序后出现往前跳 → 拒绝；
   - 单选/数字题规则重叠 → 警告但允许保存（见 6.5）。数字题只允许整数时，重叠部分里没有整数则不算重叠。多选题的重叠无法避免，不警告。
   - **永远不会命中的规则** → 警告但允许保存：数字规则的取值落在题目 `min`~`max` 之外，或 `integerOnly` 时取值中没有整数；多选 `equals` 的选项数不在 `minSelect`~`maxSelect` 之间，`containsAll` 的选项数超过 `maxSelect`。
   - **永远不会显示的题目** → 警告但允许保存：从第一题出发沿所有可能的跳转（每条规则的目标和默认去向）都到达不了的题。
10. **编辑题目的方式**：
   - 添加题目时**不接受跳转规则**（新题的选项 id 尚未生成，规则无法引用），添加后通过修改题目设置跳转；同一次修改中新增的选项也要保存后才能在规则中引用。
   - 修改题目时整体替换该题：保留的选项带原 `id`（id 不变，跳转规则不受影响），新增选项只写文字，未出现的选项视为删除。
   - 调整顺序时必须恰好包含全部题目 id。
   - 只有草稿可以修改题目（见 6.4）。
11. **编辑冲突检查**：
   - 题目修改都是“读取整份问卷 → 修改题目数组 → 写回”。写回时条件更新带上读取时的 `updatedAt`，读取后问卷被其他请求修改过则返回 409，防止后保存的覆盖先保存的。新的 `updatedAt` 保证严格大于旧值（同一毫秒内连续修改时加 1 毫秒）。
   - 请求可选带 `expectedUpdatedAt`（客户端读取问卷时看到的 `updatedAt`）：带了则与当前值比较，不一致返回 409“问卷已被修改，请刷新后重试”；不带则不检查。前端始终带上；在接口文档页面手动测试时可以省略。
   - **不使用 `version` 字段做冲突检查**，`version` 保留给第二阶段的问卷版本。

### 6.4 问卷状态
- `draft` → `published` → `closed`，不可逆（已关闭不能重新打开）。
- **发布条件**：至少有 1 道题；若设置了截止时间，必须晚于当前时间。
- **各状态下允许的操作**：

| 操作 | draft | published | closed |
|---|---|---|---|
| 修改标题、说明 | ✓ | ✓ | ✗ |
| 修改截止时间 | ✓ | ✓（只能改到当前时间之后） | ✗ |
| 修改匿名设置、提交策略 | ✓ | ✗（影响已收集答卷的统计口径和隐私承诺） | ✗ |
| 添加/修改/删除/排序题目 | ✓ | ✗ | ✗ |
| 删除问卷 | ✓（草稿没有答卷） | ✗ | ✗ |
| 填写提交 | ✗（创建者可预览） | ✓（未过截止时间） | ✗ |

- 超过 `deadline` 视同关闭，拒绝提交。不自动修改 `status`（不需要定时任务），接口返回时计算 `isExpired` 字段。
- 已发布且已过期的问卷可以延长截止时间（或改为不限），延长后恢复收集；只有主动“关闭”是不可逆的。
- 草稿不能关闭，不需要的草稿直接删除。
- 状态相关的写操作使用条件更新（过滤条件带当前状态），并发操作时只有一个成功。
- 修改时提交的值与当前值相同视为未修改，不受锁定限制（前端整份提交设置时不会被误拒）。
- 只能访问自己的问卷：访问别人的问卷与访问不存在的问卷一样返回 404，不暴露其是否存在。
- 访问未发布、已关闭或已过期的问卷时，返回明确的提示。草稿只有创建者能预览，不能提交。
- 创建者可以填写自己已发布的问卷（便于演示和测试）。
- **填写者访问问卷的各种情况**（第七步，2026-10-19 开发者确认）：

| 情况 | 获取问卷 | 路径预览 | 提交 |
|---|---|---|---|
| shortCode 不存在 | 404 `SURVEY_NOT_FOUND` | 404 | 404 |
| 草稿，访问者不是创建者 | 404 `SURVEY_NOT_PUBLISHED`“问卷尚未发布” | 404 | 404 |
| 草稿，访问者是创建者 | 200，`preview: true`，含题目 | 允许（便于测试跳转） | 409 `SURVEY_NOT_PUBLISHED` |
| 已发布、未过截止时间 | 200，含题目 | 允许 | 允许 |
| 已发布、已过截止时间 | 200，`accepting: false` 和提示，**不含题目** | 409 `SURVEY_EXPIRED` | 409 `SURVEY_EXPIRED` |
| 已关闭 | 200，`accepting: false` 和提示，**不含题目** | 409 `SURVEY_CLOSED` | 409 `SURVEY_CLOSED` |

  - 已关闭或已过期时返回 200 加提示而不是报错：填写者打开链接看到“《问卷标题》已截止”，比看到错误页面友好。
  - 提交时按收到请求那一刻的状态判断；与创建者关闭问卷恰好同时发生时，这次提交仍可能被接受（窗口极短，不加锁）。
  - 已过期的问卷延长截止时间后自动恢复接受提交。

### 6.5 已确认事项（原“待确认”，2026-10-19 开发者确认）
- 发布后不允许修改题目，只能关闭；`version` 字段为第二阶段预留。
- 单选/数字题跳转规则重叠（同一选项出现在两条规则中、数字区间重叠）：保存时**给出警告但允许保存**，由“第一条命中”兜底。
- 已关闭的问卷不能重新打开。
- 手机号等“必须为整数”的需求：按需求使用数字类型实现，在报告中说明更合理的做法是存为字符串。

### 6.6 答案校验细节
- **文本**：先去掉首尾空白；去空白后为空视为未作答。字数按 Unicode 字符数计算（一个汉字算 1 个字）。
- **数字**：答案必须是 JSON 数字，拒绝字符串和布尔值。`integerOnly: true` 时，`3.0` 视为整数并存为 `3`。
- **整数范围**：整数答案必须在 64 位有符号整数范围内（-9223372036854775808 ~ 9223372036854775807，约 ±9.2×10¹⁸），超出时按校验错误提示。原因：MongoDB 能存储的最大整数类型是 64 位（`long`），超出范围会在写入时出错；即使题目没有设置 `max` 也要检查。
- **多选**：空数组视为未作答；选项不能重复，且必须是该题的选项 id。必答但未设 `minSelect` 时，至少选 1 个。**按题目中选项的顺序保存**（不按点选先后），统计和 `equals` 判断不受点选顺序影响。
- **单选**：必须是该题的选项 id（字符串）；空字符串不算未作答，按“不是本题的选项”报错。
- **未作答**：所有题型的 `null`；文本去首尾空白后为空；多选空数组。
- **文本**补充：值必须是字符串（数字 `123` 不当作文字）；保存去首尾空白后的文字，中间的空格和换行保留。字数按 Unicode 字符（码点）计算，汉字、字母各算 1 个；部分 emoji（如带肤色、国旗）由多个码点组成，会算作多个字——与本节“按 Unicode 字符数计算”一致，不引入额外依赖（2026-10-19 开发者确认）。
- **数字**补充：拒绝 `NaN`、`Infinity`（Python 解析 JSON 时会接受这两种写法）。64 位范围检查对**所有整数值**生效，不论是否设置 `integerOnly`；小数不受此限制。`integerOnly` 时先把 `3.0` 这类小数转为整数再检查范围（如 `1e20` 转为整数后超出范围而报错）。`min`、`max` 包含边界。
- **错误提示**：`{questionId, field: "value", message}`，message 中的“第 N 题”是题目在问卷中的位置，不是在答题路径上的序号。
- **选填题**：未作答则跳过校验；一旦作答，必须满足该题全部校验规则。
- **题目设置本身**（保存时检查）：`min ≤ max`、`minLength ≤ maxLength`、`minSelect ≤ maxSelect ≤ 选项数`、选择题至少 1 个选项、各数值非负（`min`/`max` 除外）。

### 6.7 统计口径
- 按问卷的提交策略选取答卷：`latest` 只算 `isLatest: true`；`once`、`all` 算全部答卷（`once` 下每人只有一份，两种写法等价）。
- 每道题同时返回两个数（选填题没答的都不计入）：
  - **答卷数**：在上述口径内，答了这道题的答卷数；`all` 策略下同一人每次提交分别计数（人次）。单选各选项人数之和等于它。
  - **作答人数**：答了这道题的不同填写人数（按 `respondentId` 去重）。只返回数字、不暴露是谁，因此匿名问卷也返回。`once`、`latest` 下与答卷数相等，`all` 下可能小于答卷数。
- 单选：各选项人数 + 答卷数 + 作答人数；多选：各选项被选次数 + 答卷数 + 作答人数；文本：列出所有内容 + 答卷数 + 作答人数；数字：列出所有内容 + 平均值 + 答卷数 + 作答人数。
- 需求原文“总共有多少人回答”对应**作答人数**。
- 非匿名问卷的填空题内容附带填写人用户名，匿名问卷不附带（见 6.1）。
- **实现约定**（第八步，2026-10-19 开发者确认）：
  - 口径条件只在一处定义（`repositories/responses.py` 的 `scope_filter`），问卷列表的答卷数、统计、答卷列表共用，三处数字一致。
  - 单选、多选列出**全部**选项（没人选的为 0），按题目中的选项顺序；不返回百分比（前端用 选项数 ÷ 答卷数 计算）。
  - 被跳过的题、选填未答的题本来就没有存答案，不计入该题的答卷数；问卷层面另给出口径内的总答卷数、总填写人数。
  - 填空题内容按提交时间倒序。**整份统计**每道填空题只列最新 20 条并给出总数 `itemsTotal`；**单题统计**可分页查看全部内容（`offset`、`limit`，每页最多 200 条）。
  - 数字题平均值用 `$avg` 计算，没人作答时为 `null`。
  - 整份统计采用**一题一个查询**（与单题统计共用同一段代码，每次查询都能用到索引），而不是一个 `$facet` 一次算完所有题（所有题的结果在一个文档中，文本内容多时可能超过 16MB，代码也更复杂）。
  - **答卷列表**口径与统计一致（`latest` 下只含每人最新一份，不含历史版本），按提交时间倒序分页（每页最多 100 条）。
  - 草稿、没有答卷的问卷统计结果为 0 和空列表，不报错。

### 6.8 统计聚合管道

代码见 `app/stats/pipelines.py`（只构造管道、不执行，可单独测试）。下文以 `S` 表示问卷 `_id`，`Q` 表示题目 id，`口径` 为 `latest` 时的 `{isLatest: true}`（`once`、`all` 时为空）。

**（1）四种题型共用的前三步**

```js
{ $match: { surveyId: S, ...口径, "answers.questionId": Q } },  // ① 只取口径内、答了这道题的答卷（可用索引）
{ $unwind: "$answers" },                                        // ② 拆开答案数组：每个答案一条
{ $match: { "answers.questionId": Q } }                         // ③ 只保留这道题的答案
```

此时每条记录形如 `{ respondentId, submittedAt, answers: { questionId: Q, value: <这道题的答案> } }`，后面的阶段只需处理 `answers.value`。

**（2）答卷数和作答人数（各题型共用）**

```js
{ $group: { _id: "$respondentId", n: { $sum: 1 } } },                     // 先按填写人分组
{ $group: { _id: null, respondentCount: { $sum: 1 },                      // 组数 = 作答人数
                       answerCount: { $sum: "$n" } } }                     // 各组相加 = 答卷数
```

不用 `$addToSet` 把所有填写人收进一个数组再求长度：人数很多时该数组可能超过单个文档 16MB 上限。

**（3）单选：各选项人数**

```js
...前三步,
{ $facet: {
    byOption: [ { $group: { _id: "$answers.value", count: { $sum: 1 } } } ],  // value 是选项 id，直接分组
    totals:   [ ...（2） ]
} }
```

**（4）多选：各选项被选次数**

```js
...前三步,
{ $facet: {
    byOption: [ { $unwind: "$answers.value" },                               // value 是选项 id 数组，再拆一次
                { $group: { _id: "$answers.value", count: { $sum: 1 } } } ],
    totals:   [ ...（2） ]                                                    // 在再次拆开之前计数，一份答卷只算一次
} }
```

**（5）文本：列出所有内容**

```js
...前三步,
{ $facet: {
    items: [ { $sort: { submittedAt: -1, _id: -1 } }, { $skip: k }, { $limit: n },
             // 仅非匿名问卷有下面这一步：只取用户名，密码哈希等字段不会进入管道
             { $lookup: { from: "users", localField: "respondentId", foreignField: "_id",
                          pipeline: [ { $project: { _id: 0, username: 1 } } ], as: "respondent" } },
             { $project: { _id: 0, value: "$answers.value", submittedAt: 1,
                           username: { $first: "$respondent.username" } } } ],      // 匿名时没有 username
    totals: [ ...（2） ]
} }
```

**（6）数字：列出所有内容 + 平均值**

```js
...前三步,
{ $facet: {
    items:   [ ...同（5） ],
    totals:  [ ...（2） ],
    average: [ { $group: { _id: null, value: { $avg: "$answers.value" } } } ]   // 数值类型存储，$avg 直接计算
} }
```

**匿名问卷**：管道中不包含 `$lookup`，所有 `$project` 都不输出 `respondentId`。“不展示填写人”在数据库查询这一层就得到保证，不依赖应用代码事后删除字段（漏删一处就会泄露）。有测试检查管道结构和接口返回的全部字段。

**`answers` 采用 `{questionId, value}` 数组（属性模式）如何让这些管道变简单**

| 方面 | `{questionId, value}` 数组（本设计） | 如果用以题目 id 为键的对象 `{q1: "o1", q2: [...]}` |
|---|---|---|
| 管道结构 | 四种题型共用前三步，只有最后一步不同；题目 id 只是 `$match` 中的一个**值** | 每道题的字段名不同，管道要按题目拼出字段路径（`"$answers.q1"`）；无法直接 `$unwind`，需先 `$objectToArray` 转换 |
| 索引 | 一个 `answers.questionId` 索引覆盖所有题；“答了这道题”的过滤可以用索引 | 每道题一个字段，需要逐题建索引或使用通配符索引 |
| 值的类型 | 同一个字段 `value`，按题型存成不同类型：数字存数值 → `$avg` 直接算；多选存数组 → 再 `$unwind` 一次即得各选项次数；单选存选项 id → 直接 `$group` | 同样可以，但需要先解决上面的动态字段名问题 |
| 只存路径上作答的题 | 被跳过、选填未答的题没有元素，`$match` 之后天然就是“答了这道题的答卷”，不用过滤空值 | 若为每道题都留键（值为 null），统计时要额外排除空值 |
| 扩展 | 给每个答案加信息（如作答用时）只需在元素中加字段，管道不变 | 值要从标量改成对象，所有管道都要改 |

验证：`tests/test_stats.py` 检查了四种题型的管道共用前三步、匿名管道不含 `$lookup` 且不输出 `respondentId`、第一步使用索引（explain 中为 `IXSCAN`）；在开发库上用 `explain` 确认按题统计使用了 `answers_questionId` 和 `surveyId_submittedAt` 索引。

## 七、关键设计决定和理由

1. **题目嵌入问卷**
   - 题目总是和问卷一起读取（填写、编辑、统计展示），一次查询即可拿到整份问卷。
   - 一份问卷的题目数量有限，远达不到单文档 16MB 上限。
   - 只有创建者编辑问卷，不存在并发写同一文档的问题。
   - 整份问卷一次写入，保证一致性；跳转合法性检查在同一文档内即可完成。
   - 数组顺序即题目顺序，无需额外顺序字段。
   - 取舍：不支持多份问卷共享同一道题。实际问卷系统的题目复用通常是复制，以免改一题影响已发布问卷；将来可新增题库集合，复制嵌入，原结构不变。

2. **答卷单独存为集合**
   - 答卷数量没有上限，嵌入会让问卷文档无限增长。
   - 多人同时提交，写同一问卷文档会互相争抢。
   - 统计需要对大量答卷做聚合，独立集合便于查询和建索引。

3. **题目和选项都使用稳定 id**
   - 跳转规则和答卷引用 id 而不是位置或文字，调整题目顺序、修改选项文字都不会使规则和旧答卷出错。

4. **answers 采用 `{questionId, value}` 数组（属性模式 Attribute Pattern）**
   - 所有题可用同一个聚合管道统计（`$unwind` → `$match` → `$group`）。
   - 一个 `answers.questionId` 索引覆盖所有题。
   - 将来给每个答案增加信息（如作答用时）只需加字段。

5. **不冗余存储题型、统计结果**
   - 统计时本来就要读取问卷（题目标题、选项文字），题型顺带获得。
   - 统计结果由聚合管道从原始答卷实时计算，不预存，避免不一致，也支持将来新增统计维度。

6. **数字答案存为数值类型**：保证 `$avg` 等聚合计算正确。

7. **规则存为数据而不是写在代码里**：校验和跳转都是题目上的数据，程序只负责解释，满足“跳转不写死在程序里”的需求。条件使用结构化的 `{op, value}` 而不是表达式字符串，便于校验、无需解析。

8. **提交策略使用一个枚举字段而不是多个布尔开关**：只有合法状态，不会出现无意义的组合；新增策略（如 `daily`）只需新增一个取值。

## 八、为什么适合 MongoDB、不用关系表

- **题型多态**：不同题型的设置字段各不相同。关系表需要拆成题目表、选项表、校验表、规则表、答案表等多张表并大量关联，或者留出大量空列；文档模型让每种题型只存自己需要的字段。
- **问卷是天然的树状结构**：问卷 → 题目 → 选项 / 校验 / 跳转规则，文档嵌套能直接表达，读取时无需多表 JOIN。
- **答案值类型不统一**：单选是字符串、多选是数组、数字是数值，文档模型可以直接存储。
- **结构演化灵活**：MongoDB 不要求同一集合的文档字段完全一致，第二阶段新增字段时，旧文档无需迁移，程序为缺失字段提供默认值即可。
- **聚合管道**：统计需求（计数、展开数组、求平均）可直接用聚合管道完成。

## 九、可扩展性考虑（为第二阶段预留）

| 设计 | 能支持的变化 |
|---|---|
| 题目公共字段 + 题型专属的 `validation` | 新增题型（评分、日期等）只需新增 `type` |
| 题目、选项使用稳定 id | 插入、删除、调整题目顺序，修改选项文字 |
| 选项为对象 `{id, text}` | 选项配图等富媒体内容 |
| 条件 `{op, value}` 与跳转动作分离 | 多条件组合（`and`/`or`）、“显示条件”等新逻辑 |
| `settings` 集中存放 | 新增问卷设置（如限制填写人数） |
| `submissionPolicy` 枚举 | 新增提交策略 |
| `version` / `surveyVersion` | 发布后修改问卷，旧答卷可追溯版本 |
| 只存原始答卷、统计实时计算 | 交叉统计、按时间筛选、导出数据 |
| 新字段一律可选、带默认值 | 第二阶段改动无需迁移旧数据，旧功能保持可用 |
